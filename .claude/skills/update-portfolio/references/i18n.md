# Languages (English and Spanish)

Architecture, as built on 2026-11-20. The README has the short version.

## URLs

- English is the default and has **no prefix**, so every URL that existed before keeps working. Spanish lives under `/es`.
- Pages are in `app/[lang]/`. `middleware.ts` rewrites unprefixed paths to `/en/...` (the address does not change) and redirects `/en/...` to the unprefixed path. The matcher excludes `_next`, `assets`, `api` and any path with a dot (images, icons). A string like `".*\..*"` must keep **two** backslashes in the file: with one, the matcher silently matches everything and unprefixed pages 404.
- `app/[lang]/layout.tsx` is the root layout (`<html lang>`, metadata per language, `dynamicParams = false`). File-based metadata (icons, Open Graph images) stays in `app/`.
- Relative asset URLs (`src="assets/..."`, `data-background="assets/..."`) break under `/es/...`. Always write them absolute (`/assets/...`).

## What is translated

- Translated: the navbar, mobile menu, off-canvas, footer, the home page sections, the `/work` header, and the card text of every project (`data/projects.es.ts`, applied by `localizeProject`).
- English only: case studies, blog posts, the template pages (services, pricing, blog list, work-single, index-2/3). Their chrome follows the chosen language. A page whose content is translated passes `translated` to `Layout` so the translate logic knows the content language.

## Strings

- `i18n/dictionaries/en.ts` defines the shape, `es.ts` must match it (TypeScript checks). Server components get `getDictionary(lang)` and pass pieces to sections as `t` props; client components use `useLocale()`.
- Shared sections used on several pages (`Static1`, `Skills2`, `Contact1`) read the dictionary through the context. Home-only sections take a `t` prop from `app/[lang]/page.tsx`.
- Links: `components/elements/LocaleLink.tsx` replaces `next/link` everywhere and adds `/es` when needed. Plain `<a href="/projects/...">` in a page must be a `<Link>` too.
- When a pass adds a project: add its English entry to `data/projects.ts` and its Spanish card text to `data/projects.es.ts`. Missing Spanish text falls back to English silently, so check it.

## Language switch and translate behaviour (what the user asked for)

1. `EN | ES` switch in the navbar (one small button on phones). Choosing Spanish opens a module (always in Spanish) saying the site is mostly English and where the translate button is; "Continue" goes to `/es...` and saves Spanish as the visitor's language.
2. A **translate button in the navbar** (not a bar above it). First click: translates the content of the page (`#page-content`) with the browser's on-device Translator API and shows a module explaining it; later clicks toggle the original. Where the API is missing, it opens Google Translate.
3. The browser remembers the language (`localStorage`, `i18n/preferences.ts`). When a page's content language differs from the saved one (or the browser's, if none is saved), a module offers to translate, with "Always translate pages in other languages" and "Not now" (silences the offer for the visit). No other permanent button exists.
4. The button is hidden when the content already matches the visitor's language.
5. Machine translation mangles product names (for example "Pressroom"). Mark text that must not change with `data-no-translate`.

## Checks used

Routing with `curl` (`/work` 200, `/en/work` 308, `/es/work` 200, `/nope` 404), the language switch and modals with headless Chrome, the real translation against Chrome's Translator API, and the phone navbar at 390, 360 and 320 px.
